- `WizardRunCache` table: 7 columns, unique `(normalizedHost, step, cacheKey)`, expiry index.
- `ApiSpendLog` table: 8 columns, 4 indexes including `(service, createdAt)`.
- `User`: `signupIp`, `signupFingerprint`, `wizardRunsAllowed DEFAULT 1`, `lastWizardRunAt`, `suspicious DEFAULT false`.

Live end-to-end smoke (`scripts/smoke-anon-backbone.ts`) passed all 10
assertions — issue/lookup/snapshot/spend/aggregate/link/materialize/
reject-post-link-lookup — and cleaned up its rows.

The migration was hand-written rather than generated by `prisma migrate
diff` because the schema.prisma file has drift from the real DB and

the same hand-written + psql pattern until the DB is properly baselined.

### Wiring proof

`POST /api/wizard/validate` ([src/wizard/routes.ts](../domainanalyzerBackend/src/wizard/routes.ts)) now uses `authenticateOrSession()` instead of `authenticateToken`. Anonymous callers get back the same canonical-url + reachability info, no `dbExistsForUser`, and have their domain host snapshotted onto their `WizardSession`. Authenticated callers behave exactly as before.

### Signup linkage

`POST /api/auth/register` ([src/routes/auth.ts](../domainanalyzerBackend/src/routes/auth.ts)) now calls `maybeLinkWizardSession` after a successful `authService.register`. When a valid wizard cookie was present, the new user gets a `Domain` shell (with `isCompanyDomain: false`) for the host the cookie's session was working on. The cookie is cleared. Failures bubble up as `wizardLink: null` in the response — the account creation itself never fails because of linkage issues.

## What's intentionally NOT shipped yet

Everything that would change observed UX. The backbone is dormant until
the migration is applied AND a follow-up session flips routes + builds
the frontend.

### Backend follow-up

1. **Apply the migration.** `npx prisma migrate deploy`. Verify with `\d "WizardSession"` etc.
2. **Wire the rest of the wizard routes through `authenticateOrSession()`.** There are 17 wizard routes today; only `/validate` has been flipped. The pattern is mechanical but each handler reads `req.identity` and decides what to do — anon callers cannot trigger Step 5, SerpAPI, or any paid call ([antiAbuseService.canRunPaidStep](../domainanalyzerBackend/src/middleware/authenticateOrSession.ts)).
3. **Hook the runners through `recordApiSpend`.** Every external paid call (OpenRouter, SerpAPI, PageSpeed) should log USD on its way out. Without this, the budget breaker never fires. Search for `openrouter.ai`/`serpapi`/`pagespeed` in the runner files.
4. **Per-step caching against `WizardRunCache`.** Lookup-before-call in crawl, competitor, topic, and ai-run services. The table is keyed `(normalizedHost, step, cacheKey)`. Saves cost from day one.
5. **Materialize the snapshot.** `linkSessionToUser` currently only creates the `Domain` shell. The follow-up writes `CrawlSnapshot` / `Competitor` / `Prompt` rows from `WizardSession.crawlData/competitorsData/topicsData`. This requires deciding what JSON shape each step writes during the anon run — easiest if the anon and auth paths write the same canonical JSON, then `linkSessionToUser` just calls the same persister the auth path does.
6. **Real email verification flip.** [authService](../domainanalyzerBackend/src/services/authService.ts) auto-flips `emailVerified=true` at register. The defense plan calls for actually requiring email confirmation. This is a one-line change but breaks existing test flows — coordinate.
7. **Disposable-email blocklist.** Reject `mailinator.com`, `10minutemail.com`, etc at register. The list goes in env or a tiny `lib/disposableEmail.ts`.

### Frontend follow-up

1. **`/audit` route in `mode='anonymous'`.** The existing wizard at `/ai-visibility` already renders the 5-step shell. Wrap it in a router so unauthenticated `/audit` works. Reuse the same component.
2. **Signup wall at Step 4 / Step 5.** Component that renders a blurred preview of Step 5 results plus a "Sign up to see your full report" form. Submitting it hits `/api/auth/register` with the cookie already in place; the response includes `wizardLink: { primaryDomainId }` for the redirect.
3. **Client fingerprint header.** Capture canvas + UA + screen size hash, send as `X-Wizard-Fingerprint`. Reuse flagger and rate-limiter use it.
4. **Cloudflare Turnstile.** On signup AND on anon-wizard-start. Free tier; invisible for legit users.
5. **Dashboard chrome around `/ai-visibility`.** After signup-from-anon, land on the wizard results inside the dashboard, not the bare `/ai-visibility` page.
6. **Quota copy.** Show "1 of 1 audits used" in the dashboard sidebar once the user has audited. Surfaced from `User.wizardRunsAllowed` minus a count helper.

### Layer-5 (defenses tighten)

1. **`UserSignupSignal` capture + background reuse flagger.** When 3+ accounts share fingerprint or ip in a 30-day window, set `User.suspicious=true` and throttle them at the next wizard run.
2. **Behavioral signals.** Time-to-form-submit < 2s, no mouse moves between steps — aggregate into a bot score on the session.
3. **Sweeper job.** Periodically delete `WizardSession` rows where `expiresAt < now` and `linkedUserId IS NULL`. Easy cron, no business logic.

## Open product decisions still on the table

These shape the next session. Pick one and we can scope down.

1. **Signup wall placement.** Step 4 (free crawl + competitor preview, wall before AI run) is recommended. Alternative: blur Step 5 and let it run anyway.
2. **Magic link vs password on signup.** Magic link removes "remember password" UX and folds real-email-verification into the primary path.
3. **Daily budget cap value.** Default `WIZARD_DAILY_BUDGET_USD=50` in code; override via env. What's the actual ceiling we accept?
4. **Step-5 caching aggressiveness.** Cache at `(domain, prompt, model)` (safe) or at the full-run level (cheapest, but two same-domain runs return identical reports).
5. **Geo gating.** Anonymous wizard from outside the target market: block, queue, or allow?

Once the migration is deployed, smoke-test the wired `/validate` endpoint:

```
# Anonymous (no Authorization header) — should set the cookie and return mode='anon'.
curl -i -X POST http://localhost:3002/api/wizard/validate \
  -H 'Content-Type: application/json' \
  -d '{"url":"https://example.com"}'

# Re-use the cookie — should NOT mint a new one.
curl -i -X POST http://localhost:3002/api/wizard/validate \
  -H 'Content-Type: application/json' \
  -H 'Cookie: aiv_ws=<token-from-Set-Cookie-above>' \
  -d '{"url":"https://example.com"}'

# Authenticated (Bearer token) — should ignore the cookie and return mode='user'.
curl -i -X POST http://localhost:3002/api/wizard/validate \
  -H 'Content-Type: application/json' \
  -H 'Authorization: Bearer <jwt>' \
  -d '{"url":"https://example.com"}'

# Inspect a session in the DB.
psql "$DATABASE_URL" -c \
  'SELECT id, "domainHost", step, "linkedUserId", "createdAt" FROM "WizardSession" ORDER BY id DESC LIMIT 5;'
```

Then test signup linkage:

```
curl -i -X POST http://localhost:3002/api/auth/register \
  -H 'Content-Type: application/json' \
  -H 'Cookie: aiv_ws=<token>' \
  -d '{"email":"new@user.com","password":"abc123"}'

# Response should include "wizardLink": { "linked": true, "domainsCreated": 1, "primaryDomainId": N }
# And clear the cookie.
```
